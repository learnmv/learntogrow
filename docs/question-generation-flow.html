LearnToGrow Admin Flow

How Questions Are Generated

LearnToGrow uses an automated generate, review, and store pipeline. An admin chooses the curriculum scope, the backend creates an asynchronous job, the model generates JSON candidates, a reviewer prompt scores each candidate, and only approved questions are saved for students.

The Short Version

The system does not store the first answer the model returns. It treats the model output as a candidate, validates the JSON, runs an automated review, checks the minimum quality score, and stores the question only when it passes.

End-To-End Flow

1

Select Scope

Admin selects subject, grade, domains, standards, number of questions, type, review mode, timeout, and minimum review score.

2

Create Job

Backend creates a generation_jobs record and one generation_job_standards row for each selected standard.

3

Generate Candidate

Each worker builds a standard-specific prompt and calls Ollama. Local Ollama can use format: json; Ollama Cloud relies on strict JSON prompts plus backend validation.

4

Review Candidate

The reviewer prompt checks correctness, standard alignment, answer quality, explanation quality, and difficulty fit.

5

Store Approved

Only approved questions are inserted into questions. Failed candidates are rejected and recorded in audit logs.

What The Admin Controls

  • Subject and grade: narrows the curriculum area.
  • Domains and standards: chooses exactly what skills to cover.
  • Questions per standard: controls output volume.
  • Question type: multiple choice or open ended.
  • Review mode: auto review or best reviewed.
  • Timeout: maximum wait time per model call.
  • Minimum score: approval threshold, defaulting to 0.75.

What The Backend Resolves

  • Selected standards become deterministic job work items.
  • Each standard gets a target difficulty spread.
  • The model defaults to OLLAMA_MODEL unless overridden.
  • Workers run in parallel using OLLAMA_GENERATION_WORKERS.
  • Job status moves through pending, running, then completed, failed, or cancelled.

Prompt Construction

Prompts are loaded from the database, not hardcoded files. The prompt template is filled with curriculum metadata from the selected standard.

Placeholder Meaning
{grade_level} The selected standard's grade level.
{standard_code} The Common Core standard code, such as 6.EE.A.1.
{standard_description} The learning objective the question must assess.
{difficulty} A value from 0.0 to 1.0 used to tune complexity.
{keywords} Key concepts attached to the standard.
{applet_commands} Allowed GeoGebra command patterns for diagram questions. 
{
  "model": "gemma4:31b",
  "prompt": "formatted question prompt",
  "stream": false,
  "options": { "temperature": 0.7 }
}

For local Ollama, the backend can include format: "json". For direct Ollama Cloud API, the backend omits structured-output mode and then extracts and validates the raw JSON object from the model text.

Candidate Generation

The model must return a raw JSON object. The backend parses it, normalizes option text, attaches metadata, and validates required fields before it can move to review.

  • Question text must be complete.
  • Multiple choice output must contain real option text.
  • The answer must match the correct option exactly.
  • The explanation must be student-friendly.
  • Diagram questions must include GeoGebra commands.

Automatic Review

The reviewer prompt receives the generated question JSON plus the original standard context. It returns a score, approval decision, issues, and improvement notes.

  • Approved must be true.
  • Score must meet or exceed the configured threshold.
  • The reviewer must not report blocking issues.
  • If no candidate passes, the job records the best rejected score and notes.

Review Modes

Mode How It Works Best For
Auto Review
reviewed		 Generates one candidate at a time, reviews it, and stops as soon as a candidate is approved. Everyday generation where speed and quality both matter.
Best Reviewed
quality		 Generates multiple candidates, reviews them, then stores the highest scoring approved candidate. Important standards, harder topics, or batches where quality matters more than speed.

Stored Data

Approved questions are stored in questions with standard ID, text, type, options, answer, explanation, difficulty, diagram fields, and active status.

Progress Data

Generation progress is stored in generation_jobs and generation_job_standards so the admin UI can show live status.

Audit Data

Candidate, review, and repair details are stored in question_generation_audits for debugging quality failures.

Failure Handling

Candidate Failure

If the model returns invalid JSON or a structurally invalid question, the backend retries with adjusted temperature and records the failure.

Review Failure

If candidates are valid but rejected by review, the job fails that question with the best score and reviewer notes.

Ollama Failure

Connection, timeout, and HTTP errors are surfaced as job errors so the admin can retry after fixing model availability.

Job Retry

Admin can retry failed standards. The retry job keeps the same generation settings and only includes failed standards.

Important quality rule: The app should continue to treat the database as the source of truth. Prompts, GeoGebra command templates, generation jobs, audits, and stored questions should remain inspectable so question quality can be improved without guessing what the model did.

Simple Mental Model

Admin selects standards
  -> Backend creates generation job
  -> Worker builds prompt from DB template
  -> Model generates JSON candidate
  -> Backend validates structure
  -> Model reviews candidate
  -> Backend checks score and issues
  -> Approved question is stored
  -> Job progress and audit logs are updated
